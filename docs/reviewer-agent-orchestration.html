Multi-Perspective Review System

Reviewer Agent 编排蓝图

把代码评审从单一 reviewer 扩展成按风险路由的异构审查系统：不同性格、不同证据要求、不同专业盲点的 agent 独立审查，再由 Chair 汇总成可执行报告。

从单点审查到审查委员会

系统的核心不是让多个模型投票，而是让盲点不同的 reviewer 独立检查。Router 决定派谁，Reviewer 负责给证据，Chair 负责降噪和汇总。

Reviewer 性格与能力图谱

Reviewer 不按“哪个模型更强”命名，而按风险视角命名。每个 reviewer 都要有明确性格、输入、输出和典型 finding。

Spec / Plan

Requirement Integrity

追问需求是否清楚、完整、一致。

  • 目标、用户、非目标
  • 术语统一与隐藏前提
  • 失败行为和边界范围
Spec / Plan

Acceptance Criteria

把模糊愿望改写为可验收、可测试条件。

  • pass / fail 条件
  • 空状态、错误、权限
  • 验收项到测试证据
Spec / Plan

Plan Feasibility

检查计划是否能落地，是否跳步。

  • 任务拆分和依赖
  • 迁移顺序和验证点
  • 回滚和未决问题
Implementation

Spec Compliance

逐条对照 spec、plan、diff 和测试证据。

  • traceability matrix
  • 遗漏和部分满足
  • 未声明行为与 plan drift
Implementation

Correctness Auditor

只关心逻辑是否真的正确。

  • 条件判断和状态转换
  • 异常路径和幂等性
  • 并发、空值、生命周期
Implementation

Test Skeptic

不轻易相信“有测试就等于测对了”。

  • 测试是否对应验收
  • happy path 偏置
  • 过度 mock 和弱断言
Risk

Security / Abuse

按攻击者、滥用者和权限绕过视角审查。

  • 认证、授权、多租户
  • 输入、文件、secret
  • CI 和 LLM tool 风险
System

Integration / Contract

保护调用方和被调用方之间的契约。

  • API、schema、事件
  • 客户端/服务端兼容
  • 错误码和序列化格式
Domain

领域插件 Reviewer

按路径或环境触发 Unity、Web、Backend、CLI、CI 等专业审查。

  • 技术栈特定生命周期
  • 平台差异和资源约束
  • 发布、运行和维护风险

按风险等级组合 reviewer

不要让所有 reviewer 每次都跑。低风险要快，中风险要有覆盖，高风险要有异构审查和明确豁免机制。

低风险

文档、typo、小样式、非生产配置。

  • Review Router
  • Correctness 或 Maintainability
  • Review Chair
  • 快速通过，避免噪声

中风险

普通业务逻辑、多文件重构、测试变更、前后端联动。

  • Spec Compliance
  • Correctness Auditor
  • Test Skeptic
  • Maintainability Pragmatist
  • 相关领域 reviewer

高风险

鉴权、支付、迁移、CI/CD、secrets、LLM workflow、性能热点。

  • Security / Abuse
  • Integration / Contract
  • Release / Ops
  • Performance / Resource
  • 单个高置信 blocking 也要处理或豁免

Router 可以结合路径、关键词、文件类型和 artifact type。技术栈 reviewer 是插件，只在相关上下文触发。

执行流程

每轮 review 都要形成闭环：先独立审查，再合并 findings，最后修复、豁免或通过，并把经验反馈到路由和 reviewer 配置。

输入打包

收集 spec、plan、diff、测试结果、变更路径和风险标签，形成 review pack。

Router 派遣

识别 artifact type、技术环境和风险等级，选择最小但足够的 reviewer 组合。

独立审查

每个 reviewer 独立输出结构化 finding，包含 claim、evidence、impact、recommendation 和 confidence。

Chair 汇总

去重、排序、合并证据，标记 blocking、advisory、question 和 needs human decision。

修复或豁免

作者处理 blocking；无法或暂不处理的问题必须记录豁免原因、风险和责任。

统一报告样式

最终报告不应该是所有 reviewer 原文的堆叠。它要服务决策：哪些必须修，哪些可选，哪些需要人判断。

# Review Summary

Status: needs changes
Risk: high
Reviewer set: spec_compliance, correctness, security_abuse, test_skeptic, backend_api

## Blocking Findings
1. [security_abuse] export endpoint lacks object-level authorization.
Evidence: handler checks login but not project membership.
Required action: enforce membership and add regression test.

2. [spec_compliance] AC-2 is not satisfied.
Evidence: empty input still triggers backend request.
Required action: short-circuit empty input and test it.

## Advisory Findings
1. [maintainability] permission checks are duplicated in three handlers.

## Traceability
AC-1: satisfied | SearchServiceTest.testExactMatch
AC-2: missing | no implementation evidence | fix required
